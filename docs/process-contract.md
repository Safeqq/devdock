# Phase 0 Process Contract

`ServiceConfigSchema` is the runtime boundary for service settings. A service selects a named npm script in a project and records both a display path and a canonical working directory. Parsing a service config does not prove that the path exists, that the script belongs to the project, or that a port identifies the child process; those checks belong to later application and platform steps.

A run has a fresh `runId`. `processState` describes the process lifecycle (`stopped`, `starting`, `running`, `stopping`, `exited`, `failed`), while `readinessState` separately describes whether a configured probe has succeeded. `reconciliationState: unknown` records uncertain ownership after a crash. The future supervisor must not turn a successful spawn into a ready status or let events from an old `runId` change a newer run.

`ProcessAdapter` starts a process from an executable and argument array, returns a managed handle, inspects ownership, reports graceful stop capability, requests graceful or forced stop of the owned tree, and waits for exit. The handle binds `runId`, PID, identity, streams, and adapter-owned evidence. Stored PID or run history alone cannot authorize a stop. An adapter must return `ownership_unknown` if it cannot establish ownership; the supervisor must not start a replacement while cleanup is unproven.

Phase 1.2 implements `SingleServiceSupervisor` for one in-memory run. Start, stop, restart, and inspection are serialized. Each spawn receives a new UUID; a second start of an owned, running process returns the existing run. A background close observer records the exit code and changes the lifecycle state only if the handle and run ID still match. Successful spawn means `running`, while readiness remains `unknown` until a later probe is implemented. A graceful-stop timeout triggers the adapter's owned-tree fallback only after ownership inspection. If cleanup remains unconfirmed, the run stays `stopping` and a replacement is rejected.

Phase 1.3 adds a cooperative process-tree fixture. Its parent launches an HTTP child, forwards the shutdown request, and waits for that child to close before the parent exits. A native Windows integration test checks that the child's endpoint closes while an independently launched HTTP sentinel, using the same Node executable and script, stays alive. This proves the tested cooperative shutdown path and isolation from the sentinel. It does not prove forced process-tree termination for arbitrary projects; the Windows fixture adapter still reports that capability as unsupported.

Phase 1.4 shares the fixture IPC implementation between platform-checked Windows and POSIX adapters. The integration tree/sentinel test selects the adapter for the native OS; the CI workflow is configured for Windows, macOS, and Linux, but only the Windows run has been observed locally so far. These adapters retain ownership only through the live child handle. They do not create a Windows Job Object or POSIX process group, recover ownership after daemon death, or terminate a non-cooperative process tree. Both report forced tree stop as unsupported. Those missing capabilities must be resolved or explicitly bounded before general project-script support can be claimed.

Phase 3.3 begins with a per-run in-memory log buffer. It drains both managed streams, decodes UTF-8 across chunk boundaries, emits ordered log events, and keeps at most 5,000 lines or 5 MiB of text. One line is capped at 16 KiB including a truncation marker. The sequence continues across eviction so a later replay can report a gap. An authenticated per-run SSE route can replay retained events and follow new ones. `ServiceRuntimeManager` creates and registers this buffer for each real npm run before returning the Start response. The dashboard validates SSE envelopes, renders at most 500 recent rows for one selected run, reports connection loss, and closes EventSource on selection change or unmount.

`WindowsJobProcessAdapter` is the tree-aware Windows project-script adapter. It packages the PowerShell/C# Job Object helper with `@devdock/platform`, launches the absolute executable and argument array from `NpmLauncher` without a shell, and converts helper events into an adapter-owned handle, bounded readable streams, ownership inspection, forced tree stop, and terminal waiting. Completion requires the root handle to signal, Job Object active-process accounting to reach zero, and captured output to drain. Native Windows integration tests cover the direct launcher/supervisor/adapter path, authenticated lifecycle API, and dashboard. Forced stop closes the npm tree's HTTP descendant without touching an external sentinel in the adapter gate. Graceful stop remains unsupported on this adapter, and detailed restart recovery remains future work.

`ServiceRuntimeManager` owns one serialized supervisor per selected service and records snapshots under the real service ID. A repeated Start while owned returns the same run; Stop cannot target anything without the adapter-owned handle. It revalidates the stored service and package script before a new terminal run is replaced. Every supervisor transition is saved to SQLite, including natural exit from the background monitor and graceful daemon shutdown. A historical active snapshot found without an in-memory supervisor becomes `stopping/unknown`; Start is rejected and Stop remains incomplete instead of using its stored PID. This is a conservative boundary until Phase 5 adds full reconciliation.

Phase 4.1 adds preflight diagnostics without changing process ownership. Expected-port availability is checked by a short exclusive bind to `127.0.0.1`; the result is advisory and never authorizes stopping the current listener. Configured dotenv files are bounded, parsed without execution, and merged only in daemon memory. Later files override earlier files, then the pinned Node directory is prepended to `PATH`. Required key names are checked against the effective launch environment, while values are omitted from SQLite, previews, diagnostic responses, and browser state. Start fails before spawn if a configured file or required key is unavailable.

Phase 4.2 keeps process lifecycle and readiness as independent dimensions. A successful spawn first produces `running/checking`; a bounded TCP connection or HTTP 2xx response on `127.0.0.1` changes it to `running/ready`. HTTP redirects are rejected rather than followed. A timeout produces `failed/unhealthy` only after the supervisor stops the tree through the live owned handle. User Stop aborts the probe and finishes as `stopped/unknown`. Every readiness transition is persisted under the same run ID, and a probe completion is ignored when that run is no longer active.

Phases 4.3–4.4 add `ProfileRuntimeManager` above the per-service runtime. A validated DAG supplies a deterministic dependency-first order; the manager waits for each exact run ID to become usable before starting its consumer. Profile operations are globally queued so lease updates and rollback cannot race each other. A lease records the run ID, whether a profile originally started it, and every active profile consumer. Rollback and profile Stop release services in reverse topological order and call the service runtime only when the lease is profile-managed, has no remaining consumer, and still matches an owned live run. Existing, shared, changed, and uncertain runs are preserved. Startup failure ends as a visible `degraded` profile after rollback.

Phase 5 makes failure recovery explicit and bounded. A service restart policy is disabled by default; `on_failure` permits one to ten attempts with capped exponential backoff. The timer records its source run ID, and its callback rechecks the current runtime and terminal snapshot before starting a replacement. User Stop, manual Start, and daemon shutdown cancel pending restart timers. Attempts stay bounded for the daemon session rather than resetting after every brief successful spawn. Profile subscriptions retain their exact run IDs; if a ready member later exits, fails, becomes unhealthy, or loses ownership, the profile becomes `degraded` while other members keep running until an explicit profile Stop.

Daemon construction immediately scans persisted services. Any historical `starting`, `running`, or `stopping` snapshot without a live adapter handle is rewritten as `stopping/unknown` with `DAEMON_RESTART_OWNERSHIP_UNKNOWN`. This scan never constructs an adapter, starts a replacement, or kills a stored PID. Shutdown first closes HTTP admission, ends SSE clients and their heartbeat/subscription owners, cancels readiness and restart work, then stops every currently owned runtime. Log capture listeners are detached when a retained buffer is evicted or the manager closes. Snapshot callbacks, readiness results, and restart timers all compare the active runtime or run ID so delayed work cannot alter a replacement run.

Phase 6 provides production adapters for the three target OS families. Windows starts the root inside a Job Object atomically, reports graceful stop as unsupported, and terminates the owned job for forced stop. macOS and Linux start the root as a new process-group leader, report graceful stop as supported, send SIGTERM to the negative group ID, and escalate to SIGKILL only after the grace timeout. POSIX completion is reported only after the root has closed and the process group no longer exists. A signal-0 `EPERM` means the group is still present and remains under observation; only `ESRCH` proves absence. The macOS and Linux native gates both pass the stubborn-tree escalation test, and the test injects an `EPERM` probe before stop to preserve this behavior. Both adapters continuously drain child output into bounded streams and require their opaque in-memory ownership object; a persisted PID never recreates authority.

The POSIX boundary covers descendants that remain in the launched process group. A project can deliberately create a new session or process group and escape that containment, so DevDock remains a tool for trusted projects rather than a sandbox. Process-group IDs can be reused by the OS and are not recovery evidence after daemon restart. The native contract suite checks npm spawn, an HTTP descendant, sentinel isolation, natural exit, graceful stop, forced escalation for an uncooperative POSIX group, and the same supervisor/API/browser behavior on the declared runners.

Phase 0 did not include an OS adapter, supervisor, launcher, path canonicalizer, or process tree containment. Phase 1.1 adds `WindowsFixtureProcessAdapter` for the cooperative Node fixture. It keeps a live child handle and an in-memory launch identity; neither can be reconstructed safely from a stored PID. Graceful stop uses fixture IPC. Forced process-tree termination remains unsupported and must not be reported as successful. General native lifecycle behavior remains part of Phase 1 and the cross-platform release gate.
