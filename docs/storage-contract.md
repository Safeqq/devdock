# Phase 2 registry and storage contract

The application registry accepts a user-selected, trusted project directory. It resolves the display path to a canonical filesystem path and records a filesystem identity where available. Registration deduplicates by canonical path or identity. A path whose recorded identity changes is rejected until the conflict is resolved. An archived project is hidden from the active list and cannot be used to discover or launch scripts. Archiving only changes SQLite metadata; it never deletes the source directory. Registering the same directory again restores its record and original ID.

Service cwd must resolve inside the canonical project directory. A symlink that escapes the project is rejected, as is a `package.json` symlink to a file outside it. Windows UNC paths are currently unsupported and rejected. Network drives mapped to letters and symlink behavior beyond the tested local path case still require native testing. The registry retains the display path for users and the canonical path for identity checks.

Discovery reads at most 1 MiB of `package.json`, parses JSON as data, and lists string-valued script names. It does not run scripts, install dependencies, or load environment files. Invalid JSON and invalid `scripts` shapes get explicit error codes. The user must select a discovered script before a service record is created. The registry rechecks the project identity, cwd, and script before producing a launch plan. A script name cannot start with `-` or contain control characters.

The launch plan uses the pinned Node executable and its bundled npm CLI with separate arguments: `node npm-cli.js run <script>`. It passes a canonical cwd and a small allowlist of inherited environment variables. Explicit environment files are parsed as data in configured order, with later files overriding earlier files; the pinned Node directory is prepended to the final `PATH`. Windows treats environment keys case-insensitively and emits one `Path` entry; POSIX reads only the case-sensitive `PATH` key. Environment references must stay inside the real service cwd, including when the cwd itself is reached through a supported directory symlink, and Start rejects a file whose resolved target escapes that root. Daemon-only variables are not inherited by default. npm executes script contents using its own script shell, including npm lifecycle hooks; only trusted repositories should be registered. `ServiceRuntimeManager` wires the plan to a Windows Job Object or POSIX process-group adapter and persists snapshots observed through Start, status, Stop, and daemon shutdown.

SQLite schema version 2 uses `PRAGMA user_version`, foreign keys, strict tables, and WAL for file databases. Version 1 created projects, service configurations, run snapshots, and application settings; version 2 adds profile configurations without replacing those tables. Migrations and project registration run in short transactions; dynamic values use prepared statement bindings. Service JSON stores environment file references, required key names, optional readiness configuration, and the bounded restart policy, never environment values. Older service JSON receives the default `{ "kind": "off" }` policy during runtime validation. Profile JSON stores member service IDs and dependency edges. Run snapshots persist process and readiness states separately. Profile operation ownership, shared-use leases, pending restart timers, and restart-attempt counters remain in memory and are not reconstructed after daemon restart. Snapshot metadata is historical and never proves current process ownership; active historical snapshots are conservatively reconciled to unknown when the runtime manager starts. Environment values and raw logs are not stored. Stored JSON is checked against runtime schemas on read and write. A database from a newer schema version is rejected without migration. Back up a database before a future migration; there is no downgrade path yet.

Configuration export is derived from validated registry records and does not copy the SQLite representation. Schema version 1 replaces database UUIDs with document-local service references and converts service cwd values to path segments relative to the project root. It exports environment file references and required key names, but never reads or exports their values. Project paths, canonical filesystem identity, run snapshots, logs, settings, and in-memory ownership state are omitted. Import is not implemented in v1, so an export is a reviewable configuration record rather than a backup of runtime authority.

The data directory resolver chooses `%LOCALAPPDATA%\DevDock` on Windows, `~/Library/Application Support/DevDock` on macOS, and `${XDG_DATA_HOME:-~/.local/share}/devdock` on Linux. A relative environment override is ignored. Callers can open a registry database at a filename in that directory; tests use temporary paths. The SQLite driver is Node.js 24.21.0's built-in `node:sqlite`, whose API is currently marked Release Candidate in Node documentation. This choice avoids a native addon for the pinned runtime, but later runtime upgrades need compatibility testing.
