# Windows Job Object containment spike

The Windows integration spike uses a PowerShell 5.1 test helper with a small C# P/Invoke class. It creates an unnamed Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and passes its handle through `PROC_THREAD_ATTRIBUTE_JOB_LIST` to `CreateProcessW` with `EXTENDED_STARTUPINFO_PRESENT`. The root process joins the job atomically during creation, before it can run. The helper also checks membership with `IsProcessInJob`. Only a null stdin and the two output write handles are inherited through `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`. The fixture starts a detached HTTP child and deliberately exits. The helper still reports one active job process, and the HTTP child responds. `TerminateJobObject` brings the active count to zero and closes that endpoint; a separate HTTP sentinel using the same Node executable and script remains responsive. Killing the helper unexpectedly closes the job handle and also stops the orphaned child. The helper holds kernel handles, not a PID reconstructed from history.

Child stdout and stderr are forwarded as base64 JSON events. Two reader threads continuously drain the Windows pipes into a queue capped at 128 chunks of 4 KiB. If the caller stops reading and the queue fills, new bytes are discarded and later reported in a `job-output-gap` event. This keeps the service pipe moving and bounds queued binary output to 512 KiB. `WindowsJobProcessAdapter` exposes decoded byte streams and adds a 64 KiB high-water mark per stream; the daemon `RunLogBuffer` remains responsible for UTF-8 decoding, line limits, sanitization, and retained log limits when the run is registered with the daemon.

A C# monitor owns natural-completion observation. It publishes `job-exited` only after the root process handle is signaled, Job Object active-process accounting reaches zero, and the output writer has drained its bounded queue or published its gap. The event carries the root process exit code, then the helper exits successfully. An atomic lifecycle decision prevents a concurrent explicit Stop and natural exit from both publishing terminal events. A root PID ending while a descendant remains in the job is therefore not treated as service completion.

Before process creation, the Node caller sends the environment selected by `NpmLauncher` in a base64 envelope. PowerShell decodes the payload explicitly as UTF-8, and the C# helper validates variable names, rejects case-insensitive duplicates, caps the block at 256 entries and 1 MiB, sorts it case-insensitively, and passes a double-null-terminated UTF-16 block with `CREATE_UNICODE_ENVIRONMENT`. `CreateProcessW` no longer receives a null environment pointer, so daemon-only variables inherited by the PowerShell helper do not reach the managed process. The base64 envelope is needed because Windows PowerShell 5.1 console input otherwise decodes non-ASCII JSON using its active console code page.

The same launch payload carries an absolute executable path, an argument array, and an absolute canonical cwd. `CreateProcessW` receives the executable separately as `lpApplicationName`, so executable discovery never falls back to a shell. The helper builds `lpCommandLine` by quoting every argument with the Windows backslash-before-quote rules, preserves empty arguments and trailing backslashes, caps the array at 256 entries, and rejects command lines at the Windows 32,767-character boundary.

The helper is packaged as `packages/platform/assets/windows-job-helper.ps1`. `WindowsJobProcessAdapter` starts it without a shell, translates its protocol into an adapter-owned handle and bounded readable stdout/stderr streams, reports ownership, requests forced tree termination, and waits for the terminal job event. `SingleServiceSupervisor` has been tested with a real `NpmLauncher` plan in a cwd containing spaces, Unicode, and shell metacharacters. The managed npm script and its HTTP descendant stop while a separate Node sentinel remains responsive. `ServiceRuntimeManager` connects the adapter to authenticated daemon Start/status/Stop routes and per-run SSE. The Windows browser gate now exercises these controls, receives live and replayed logs, and proves that closing the tab leaves the daemon-owned service running until an explicit Stop. The adapter does not implement graceful stop. The previous suspended-create-then-assign sequence had a crash window before assignment; the [job-list process attribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) closes that window for the root process. [Microsoft explains the race](https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812).

The local tests run through `npm run test:integration` on native Windows x64 and are skipped on macOS/Linux. They verify a cwd and script path containing spaces and Unicode; exact argument round-trips for empty strings, quotes, backslashes, Unicode, whitespace, and shell metacharacters; forwarded Unicode stdout/stderr; a Unicode environment value; exclusion of a daemon-only secret; a natural nonzero root exit reported only after output completion; an explicit job stop; unexpected helper death; bounded behavior while the caller pauses during 16 MiB on each output stream; and the complete npm launcher/supervisor/adapter path. They do not cover all Windows versions, CPU architectures, arbitrary non-Node executables, graceful stop, daemon restart recovery, or protection against a process that deliberately escapes supported containment. The [Job Objects documentation](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) describes default child membership and `KILL_ON_JOB_CLOSE`; the [CreateProcessW documentation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) describes the extended startup attributes and explicit executable paths.
