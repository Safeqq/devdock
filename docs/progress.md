- Runtime Node.js menjalankan daemon dan fixture. npm memasang dependensi dan menjalankan script workspace. Versi keduanya perlu dipin agar hasil setup dapat diulang.
- Schema runtime memeriksa data saat program berjalan; tipe TypeScript saja hilang setelah kompilasi. Readiness fixture membuktikan server menjawab request, sedangkan spawn baru membuktikan proses mulai.
- Child process adalah program fixture yang diluncurkan CLI. Handle adapter adalah bukti ownership selama sesi itu hidup; angka PID dari histori saja tidak memberi hak aman untuk menghentikan proses.
- Pada Node.js, event `exit` dapat datang sebelum output terakhir selesai; event `close` menandai penutupan stdio. Supervisor menunggu `close` agar status final tidak ditulis dua kali dan output fixture tidak terpotong.
- Child fixture adalah turunan parent yang dimiliki supervisor. Sentinel adalah proses terpisah di luar run itu. Kesamaan executable dan script tidak memberi hak untuk menghentikan sentinel; stop harus mengikuti ownership run.
- Adapter POSIX produksi memakai process group karena satu PID parent tidak membuktikan semua descendant berhenti. SIGTERM memberi kesempatan cleanup pada seluruh group, lalu supervisor memakai SIGKILL bila grace timeout habis. Hanya tes native macOS/Linux yang dapat membuktikan syscall dan signal behavior tersebut; WSL tidak membuktikan jalur Windows Job Object.
- Pada Fase 2, canonical path dan identitas filesystem mencegah registry memperlakukan lokasi yang berubah sebagai proyek lama. TypeScript tidak memvalidasi JSON saat runtime; parser dan schema runtime dibutuhkan sebelum data masuk SQLite atau launcher. `package.json` dibaca sebagai data, tetapi `npm run` sengaja mengeksekusi script proyek terpilih beserta lifecycle hook npm.
- SBOM menjawab komponen produksi apa yang ikut dalam paket, sedangkan inventaris lisensi merangkum deklarasi yang diterbitkan komponen tersebut. Deklarasi yang lengkap tidak otomatis membuktikan kompatibilitas lisensi; keputusan hukum dan lisensi proyek tetap perlu dibuat secara eksplisit.
- Pada 3.1, loopback membatasi alamat yang dapat menerima koneksi, tetapi browser pada mesin yang sama tetap membutuhkan sesi karena halaman lain dapat mencoba mengirim request ke localhost. Token CSRF membuktikan mutasi berasal dari halaman yang dapat membaca respons same-origin; `SameSite` dan pemeriksaan Origin menambah batas tambahan.
- Pada bagian API 3.2, command preview adalah data tentang eksekusi yang mungkin dilakukan, bukan izin menjalankan proses. URL Open App dibuat dari port yang divalidasi dan tidak membuktikan aplikasi siap menerima request.
- Pada UI 3.2, halaman pairing harus tersedia sebelum autentikasi agar browser baru dapat memasukkan kode. Asset statis boleh publik karena tidak memuat secret; data proyek tetap berada di balik session. Schema respons runtime mencegah UI memperlakukan JSON yang rusak sebagai fakta server.
- Pada fondasi log 3.3, satu chunk stdout dapat berakhir di tengah karakter UTF-8 atau baris. Decoder dan buffer menyimpan fragmen kecil sampai batas; sequence menandai urutan event diterima daemon, sedangkan gap memberi tahu pembaca bahwa cursor lama tidak bisa direplay sepenuhnya.
- Pada SSE 3.3, `Last-Event-ID` membuat reconnect meminta event setelah sequence terakhir yang terlihat browser. Bila event itu sudah terbuang dari ring buffer, event `gap` mencegah UI menganggap riwayat masih lengkap. Menutup koneksi lambat menjaga penangkapan stdout/stderr tetap berjalan; browser dapat menyambung lagi.
- Pada adapter Windows, Job Object adalah sumber ownership untuk tree. `PROC_THREAD_ATTRIBUTE_JOB_LIST` memasukkan root saat `CreateProcessW`, sebelum thread-nya berjalan, sehingga tidak ada jendela gagal antara create dan assign. `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` membuat child ikut berhenti saat helper kehilangan handle job. Reader pipe harus tetap menguras output walaupun consumer lambat; antrean bounded memutus hubungan antara laju service dan laju caller, sedangkan event gap membuat kehilangan data terlihat. Handle TypeScript menyimpan bukti ownership yang hanya dikenal instance adapter sehingga PID dari database tidak dapat dipakai untuk menghentikan proses.
- Environment block Windows adalah rangkaian `nama=nilai` berformat UTF-16 yang diakhiri dua karakter NUL. Memberikan pointer block secara eksplisit mencegah child menerima seluruh environment helper. Payload launch juga perlu encoding eksplisit karena code page stdin PowerShell 5.1 tidak selalu UTF-8.
- `CreateProcessW` menerima executable dan satu string command line, bukan array argumen. Adapter harus mengubah array menjadi string dengan menggandakan backslash sebelum quote dan sebelum quote penutup; sekadar membungkus setiap nilai dengan quote akan merusak trailing backslash. `lpApplicationName` yang eksplisit memastikan metakarakter tidak memanggil shell.
- Selesainya PID root belum berarti service selesai karena descendant mungkin masih aktif di Job Object. Event terminal baru aman setelah handle root signaled, accounting job nol, dan output EOF sudah dikuras. Exit code pada event berasal dari handle root; exit code helper hanya menunjukkan protokol helper selesai dengan benar.
- `NpmLauncher` hanya menyusun executable, argumen, cwd, dan environment. `WindowsJobProcessAdapter` menyediakan containment native, sedangkan `SingleServiceSupervisor` mengatur transisi lifecycle. Pemisahan ini membuat kontrak supervisor tetap sama ketika adapter POSIX nanti memakai mekanisme OS yang berbeda.
- `ServiceRuntimeManager` menjadi composition layer antara registry dan supervisor: registry memvalidasi pilihan tersimpan, supervisor menjaga satu lifecycle per service, buffer menyerap stream, dan API hanya mengirim fakta hasil operasi. Serialisasi per service mencegah dua request Start bersamaan membuat dua tree tanpa memblokir operasi service lain.
- Snapshot SQLite menjelaskan histori, bukan bukti ownership. Setelah daemon baru tidak memiliki handle adapter lama, status aktif historis harus menjadi `unknown`; menyimpan PID tidak membuat Stop aman.
- Dashboard hanya membuka satu `EventSource` untuk service/run yang sedang dipilih dan menutupnya ketika pilihan berubah atau komponen dilepas. Menutup tab hanya membersihkan koneksi pengamat; lifecycle service tetap dimiliki daemon dan tidak ikut berhenti.
- Buffer daemon dapat menyimpan hingga 5.000 baris atau 5 MiB per run, sedangkan dashboard hanya merender 500 baris terbaru agar tampilan tetap bounded. State readiness tetap ditampilkan terpisah dari process state karena log atau PID tidak otomatis membuktikan aplikasi siap.
- Project dengan service aktif atau ownership unknown tidak boleh diarsipkan karena tindakan itu akan menyembunyikan kontrol atas run yang belum selesai atau belum dapat direkonsiliasi.
- Port `available` hanya menyatakan bind loopback berhasil pada saat pemeriksaan. Proses lain dapat mengambil port sesudahnya, sedangkan status `in_use` tidak membuktikan siapa pemilik listener. Karena itu diagnostics tidak memberi otoritas untuk kill atau mengganti port.
- Environment diagnostics memeriksa nama key terhadap environment launch efektif. Key yang ada belum membuktikan nilainya benar; nilai sengaja tidak dikirim ke browser atau disimpan di SQLite. File terakhir dalam daftar mengalahkan key yang sama dari file sebelumnya.
- Process state dan readiness state menjawab pertanyaan berbeda. `running/checking` berarti tree proses masih dimiliki tetapi endpoint belum lulus probe; `running/ready` berarti endpoint yang dikonfigurasi sudah memberi hasil sehat. Respons TCP atau HTTP tetap tidak membuktikan identitas proses yang menjawab.
- Probe readiness berjalan di latar belakang agar request Start tidak menunggu seluruh timeout. Probe harus dapat dibatalkan dan terikat pada `runId`; tanpa guard tersebut, hasil lambat dari run lama dapat menimpa state run pengganti.
- DAG mengizinkan satu service memiliki beberapa dependency tanpa memaksa urutan yang tidak diperlukan. Topological order menjamin dependency muncul sebelum consumer; cycle harus ditolak saat konfigurasi karena tidak memiliki titik awal yang valid.
- Kepemilikan profile tidak berasal dari nama service atau PID. Lease menyimpan run ID yang benar, asal run, dan himpunan consumer. Run pre-existing selalu dipertahankan saat rollback, sedangkan run yang dimulai profile baru boleh dihentikan setelah consumer profile terakhir lepas.
- Rollback berjalan terbalik dari urutan start agar consumer dilepas sebelum dependency. Hasil parsial tetap terlihat sebagai `degraded`, termasuk service yang gagal, berhasil di-rollback, atau sengaja dipertahankan.

- Bug portability yang ditemukan pada macOS berasal dari dua nama path untuk direktori temporer yang sama: input dapat memakai `/var/...`, sementara `realpath` file menghasilkan `/private/var/...`. Checkout Windows juga mengubah LF menjadi CRLF dan membuat formatter CI gagal, sehingga repository sekarang menetapkan LF melalui `.gitattributes`.
- Pada POSIX, signal 0 tidak mengirim signal tetapi memeriksa keberadaan target. `ESRCH` berarti process group tidak ada; `EPERM` berarti kernel menemukan target tetapi caller tidak diizinkan mengirim signal. Karena itu `EPERM` harus mempertahankan ownership dan polling, bukan mengubah run menjadi `unknown` atau menganggap cleanup selesai.
- Profiling harus memisahkan kehilangan pada adapter dari eviksi retention. Burst awal yang tidak dipacu menghasilkan marker/byte yang hilang sebelum buffer penuh; workload final dipacu sampai adapter melaporkan nol byte hilang, lalu `gap` dan selisih event benar-benar mengukur eviksi buffer 5.000 baris.

## Blocker dan batas dukungan

- Di runner GitHub windows-2025, port DevTools WebView2 (`--remote-debugging-port` lewat `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`) tidak terbuka, walaupun aplikasi terpasang berjalan normal dan menampilkan jendelanya.
  - Karena itu penggerakan halaman aplikasi terpasang hanya diverifikasi lokal; CI memakai `--engine-only` dan `--shell-only`.
  - Penyebab port tertutup tidak diselidiki lebih jauh.
- Installer belum ditandatangani (SmartScreen memperingatkan), belum ada pembaruan otomatis, dan aplikasi desktop baru untuk Windows x64.
- Instalasi Node/npm sistem (`24.11.1`/`11.6.2`) masih lebih lama; verifikasi memakai runtime portable yang dipin. Pengguna perlu memasang versi pin atau memakai runtime setara agar `npm ci` lulus dengan `engine-strict`.
- `WindowsJobProcessAdapter` tetap tidak memiliki cooperative graceful stop; capability-nya sengaja `unsupported` dan shutdown memakai forced Job Object termination. Adapter POSIX hanya memiliki authority atas proses yang tetap berada dalam process group; project tepercaya dapat sengaja membuat session/group baru dan keluar dari containment. Rekonsiliasi daemon tetap konservatif: run aktif historis diblokir sebagai `unknown`; inspeksi metadata lintas restart, auto-adoption, dan recovery interaktif belum tersedia.
- Matriks Phase 6 telah lulus pada ketiga runner, tetapi dukungan hanya diklaim untuk kombinasi OS/version/architecture dan toolchain yang dicatat. Probe hanya membuktikan endpoint loopback merespons, bukan identitas listener. Snapshot operasi profile, lease, pending timer, dan penghitung restart sengaja hanya berada di memori karena restart daemon menghilangkan bukti ownership. `node:sqlite` masih ditandai Release Candidate pada Node 24.21.0.
- Seluruh subfase dan gate lintas platform Fase 7 sudah terverifikasi pada commit `6c5707a`, lalu suite yang sama kembali lulus pada checkpoint README `8d36ff0`. Rekaman Fase 7.4 tetap berupa artefak lokal ignored dan belum dipublikasikan; publikasi bersifat terpisah dan memerlukan otorisasi pengguna.
- Rilis 0.1.0 hanya tersedia sebagai GitHub Release; tidak ada publikasi npm (nama `devdock` sudah dipakai package lain) dan rekaman demo tidak dirilis. Artefak `devdock-0.0.0.*` lama masih ada di `artifacts/` yang di-ignore dan bukan bagian rilis.
- Margin CI yang perlu dipantau: ekstraksi tarball Windows 131,2 detik dari batas 240 detik, sedangkan halaman pertama browser test di Ubuntu sudah dipindahkan ke hook pemanasan (`47fcb46`).
- Tooling rilis (version check, package evidence, artifact verifier, fresh repack, SBOM, dan inventaris lisensi) lulus pada workflow tiga OS di commit `d329d1c`. `release:version`, readiness inspector, dan `verify:package` tetap hanya dijalankan lokal pada Windows karena workflow tidak memanggil command tersebut secara langsung; test-nya lulus pada ketiga runner melalui suite unit dan integration.
- Isi tarball kini 3.448 entry pada lokal dan ketiga runner; tarball Windows CI byte-identik dengan lokal dari tree yang sama. Reproducibility byte tetap per keluarga OS, bukan lintas keluarga OS.
- Timeout browser Ubuntu dan packaged CLI Windows dijelaskan oleh data per langkah di `7ea89ea` (cold start Chrome 22 + 8 detik; ekstraksi tarball 86,6 detik). Penyesuaian test baru verified lokal dan menunggu matriks berikutnya. Penyebab kelambatan pada kedua runner tidak diselidiki lebih jauh.
